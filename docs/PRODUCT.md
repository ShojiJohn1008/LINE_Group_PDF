# プロダクト整理 — LINEグループ資料アーカイブ

技術仕様は [README.md](../README.md)、実装の判断ログは
[IMPLEMENTATION_LOG.md](IMPLEMENTATION_LOG.md) を参照。このドキュメントは
「誰のどんなペインを、どう解くプロダクトか」を整理するものです。

## 1. 一行で

**LINEグループに貼るだけで、論文・資料が要約と索引つきで自動的に検索可能な
アーカイブになる。** 投稿者は今まで通りLINEに貼るだけ。Driveへの再アップ・
命名・整理の手作業はゼロになる。

## 2. 誰の・どんなペインか

最初のターゲットは1グループに固定する：**私立総合病院・総合診療科のLINE
グループ**。

このグループでは、カンファレンスや抄読会で話題に上がった論文を、T先生が
LINEに共有してくれる。共有知が自然に流れている良いグループ。問題は「流れた
後」にある。

### 第1層：在庫化の手作業（キュレーターの二重投稿）

- 今、論文を後から参照できる状態に保つために、T先生は **LINEに貼る → さらに
  Dropboxにも共有する**、という二段を毎回踏んでいる。
- LINEは流れて消えるから、誰かが手でDropboxに在庫化しないと残らない。その
  「誰か」がT先生一人に集中している。命名も整理も手作業。
- これは続ける人の善意に依存していて、摩擦が大きい。忙しければ抜ける。
- **解：LINEに貼る＝在庫化、にする。** Botが投稿を拾い、要約し、
  `YYYY-MM-DD_種別_内容ラベル` で命名し、月別フォルダに保存し、
  `references.md` に追記する。Dropboxへの二重投稿ステップが丸ごと消える。

### 第2層：「自分では作れない／回せない」

- このパイプライン（Webhook受信・LINE署名検証・PDF/URL抽出・OpenAI要約・
  Drive保存・索引追記・失敗時のグレースフル劣化）を、現場の医師が自前で
  立てて運用するのは非現実的。
- **解：管理者はBotをグループに1個追加するだけ。** サーバー・Drive・要約API
  の課金といった中間インフラは提供側が肩代わりする。

## 3. Before → After

| | Before（現状） | After（導入後） |
|---|---|---|
| 投稿者の操作 | LINEに貼る **＋** Dropboxに再共有 | LINEに貼る **だけ** |
| 命名 | 手作業 | 自動（日付_種別_内容ラベル） |
| 整理 | 手作業 / されない | 月別フォルダに自動分割 |
| 要約 | なし | OpenAIで日本語の要点＋タグ |
| 探す | LINEを遡る / Dropboxを探す | `references.md`を時系列で一覧 |
| 続くか | キュレーターの善意依存 | 投稿するだけで自動継続 |

実挙動はコードに実装済み：Japan時間での月別フォルダ、内容ラベル優先の
ファイル名、PDF本文抽出、要約失敗時も保存は継続（資料を取りこぼさない設計）。

## 4. セルフホスト vs マネージド（課金がどこに乗るか）

このシステムは同じものの裏表で2つの道がある。

- **セルフホストの道（無料）** — コードはOSS。技術がある人は自分でサーバーを
  立てて動かせる。原価は自分のサーバー・Drive・OpenAIキー。
- **マネージドの道（有料）** — 提供側が中間インフラを回す。課金は「機能」では
  なく「**サーバーをあなたの代わりに回す**」への対価。要約API・ストレージ・
  常設サーバーという毎月のランニングコストを肩代わりする部分にだけ課金する、
  オープンコア／マネージド型。

無料と有料の線を最初から引いておく（例：要約○件/月までは無料、超過や長文
分割・OCRは有料、など）。原価ラインは第6節に対応する。

## 5. 隣のプロダクトとの違い

参照点としてObsidianコミュニティプラグイン「LINE Notes Sync」がある。混同
しないために違いを明示する。**模倣ではなく隣接市場。**

| 軸 | LINE Notes Sync | このプロダクト |
|---|---|---|
| 対象 | 個人のLINE（n=1） | LINE**グループ**の共有知 |
| 運ぶもの | テキスト/画像を**そのまま**同期 | PDF/URLを**要約・タグ・索引化** |
| 出力先 | Obsidian（個人の第二の脳） | Drive＋時系列索引（チームの資料棚） |
| AI | なし | あり（要約・タグ） |
| 解くペイン | 個人のキャプチャ摩擦 | キュレーターの在庫化手作業 |

「個人メモ同期」ではなく「**グループ資料の要約アーカイブ**」。ここが顔つき。

## 6. プロダクト化に今足りないもの

最初の1グループに入れるだけなら現状コードで動く。複数顧客に配るには宿題が
ある（正直に列挙）。

- **マルチテナント化** — 今は `.env` 1セット ＝ 1グループ ＝ 1Drive。複数
  グループ/病院を1サーバーで捌く設計（テナント分離・Drive割り当て）がない。
- **オンボーディングの摩擦** — 今はngrok手動公開＋Drive OAuth手動。管理者が
  「Bot追加だけ」になるには、この手順を提供側に寄せる必要がある（常設デプロイ、
  OAuth代行 or サービスアカウント＋共有ドライブ）。
- **重複・取消対応** — 同一URL/同一イベントの重複と、送信取消が未処理
  （READMEの既知の制限どおり）。グループ運用では重複が出やすい。
- **コスト境界** — 要約は先頭24k文字クリップ、スキャンPDFのOCRなし、長文PDFは
  冒頭のみ。課金プランを引くなら、ここが原価ラインかつ無料/有料の分岐点。
